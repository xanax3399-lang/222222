# Исследование остановки NL для CS:GO

Пользователь уточнил: противник убивает его **раньше выстрела**, речь не о
Desert Eagle и не о промахах по десинку. Рабочая задача — установить задержку
до выстрела и возможность переноса остановки. Перенос полного resolver сам по
себе не исправляет неустановленную причину задержки.

В присланном `module_diagnostics.log` переход точек установлен, но `Calls: 0`.
Время снимка относительно боя неизвестно. Этот файл не подтверждает выполнение
перехода в бою и не содержит скорости, времени готовности оружия или причин
отказа в выстреле. Причина задержки по нему не установлена.

## Что восстановлено

Донор — именно x86-ядро NL для CS:GO, база `0x412A0000`, SHA-256
`682ce73b371349f87da6fd9365f8550e240dcdb97951e80445e70286275ad96e`.
Код и выгрузки CS2 в исследовании не используются.

`nl_stop_math.hpp` содержит два блока с явными входами:

| Блок | Инструкции донора | Граница результата |
|---|---|---|
| Трение | `0x414A09B7..0x414A09C6`, `0x414A0A6A..0x414A0ABE` и ветка без изменения | Скорость после трения и масштабирование вектора. Значения ConVar, interval и surface friction передаются явно. |
| Команды торможения | `0x414A0D43..0x414A10E8`, достижимые ветки | Компоненты движения с ограничением ±450, включая ветку малого импульса на земле. Направление и состояние передаются явно. |

На 1040 наборах трения и 1256 наборах торможения C++ дал побитно одинаковые
float32-результаты с **исходными инструкциями**, без исправления их байтов.
Ещё 42 случая проверяют отказ при NaN/Inf без изменения выходного буфера.
Отчёт — `../../reports/stop_math_validation.json`.

Математика находится в `../../source/skeet/nl_stop_math.h`; прежний путь
`nl_stop_math.hpp` включает этот production-заголовок. Блок трения остаётся
исследовательским. **Блок импульса подключён к DLL** переходником
`nl_stop_patch.h`. Он не определяет момент начала остановки и не меняет
атаку, минимальный урон или hitchance.
В проверке не выполняются чтение ConVar, инициализация TLS и расчёт направления
через atan2/sin/cos: их результаты/состояние задаются явно.

## Связи с остальным кодом

По ссылкам `sv_friction`, `sv_stopspeed`, `sv_accelerate` из исходной оболочки
исследована функция `0x414A0210`. В ней видны порог `0.323 * max_speed`,
чтение названных ConVar, изменения полей команды `+0x24`, `+0x28`, `+0x30`
и отдельные условия по конфигурации оружия. Это основание для дальнейшего
исследования остановки, а не доказательство восстановления всех её режимов.

Найден прямой вызов `0x4147A5EC`. Перед ним готовятся четыре стековых аргумента:
выходная структура `context+0x120`, команда `context+0x12C`, результат helper
`0x4148C480` и адрес флага `context+0xF0`. После вызова проверяется этот флаг.
Следовательно, заменить только формулу трения недостаточно: требуется
установить контракты вызывающего кода, копии команды и последующей симуляции.

`seeds.csv` — список кандидатов для анализа. Названия не являются исходными
символами NL. Псевдокод Ghidra с ошибками потока управления не считается
собираемым исходником и не используется в DLL.

## Подключение к GS

Родная остановка GS — `0x43388405`; прямые вызовы: `0x433702FB`,
`0x43372C65`, `0x433CE122`. Последний применяется и к копии команды при
симуляции движения. У функции custom ABI: ECX — игрок, EDX — команда,
XMM0/1/2 — скорость, один стековый аргумент — выходные углы, RET 4, результат AL.
Родные решение о вызове, трение, углы против скорости, кнопки и последующая
симуляция сохраняются.

Переход стоит в `0x433886E4`, после родного helper ускорения `0x433AC9C0`.
В его кадре ESP+8 — эффективная wishspeed, ESP+0x20 — ускорение,
ESP+0x1C — скорость после трения. ESI указывает команду, EDI — игрока.
Флаг земли читается через тот же разрешённый GS offset m_fFlags, что и helper.
NL получает эти явные входы и единичный surface factor; собственная физика
поверхности и выбор maxspeed NL здесь не подключены. Его результат меняет
только forwardmove в уже подготовленном GS направлении против скорости.

При успехе выполняется переход в `0x433886F8`, минуя старую проверку GS,
которая могла заменить импульс на 0.001. При неподдержанном численном контексте
выполняются исходные инструкция и ветка GS. Шим сохраняет GPR, флаги и полный
x87/SSE-контекст. Установка проверяет байты и фиксированную базу, готовит RX
шим до правки ядра, откатывает правку при ошибке flush. Установка происходит
до контрольной суммы/подготовки VM; таблицы VM не перекрывают переход.

`validate_stop_bridge.py` исполняет скомпилированный production-переходник,
все три прямых CALL и **оригинальные инструкции остановки, трения и helper
ускорения GS**. Игрок, vtable, ConVar и внешняя CRT atan2 заданы фикстурами.
Ожидаемый импульс получается из исходного x86-блока NL. Проверяются углы,
кнопка атаки, RET 4, регистры/FP, режимы, выключение INI и откат установки.
Отчёт — `../../reports/stop_bridge_validation.json`.

Режимы 2/4 включают этот переход при `[movement] nl_brake=1`; 0 оставляет
старый GS, сохраняя точки NL. Пункт 5 сохраняет число обращений к переходнику
(после трения), применения/возвраты к GS и последний численный пример.

Полный контроллер условий/сроков остановки NL ещё не перенесён. Для оценки
задержки до выстрела и поведения на карте требуется проверка в самой CS:GO.
Сборка, эмулятор и Windows LoadLibrary не доказывают более ранний выстрел.

## Воспроизведение проверки

Из каталога `gamesense-csgo`, после установки `requirements-build.txt`:

```sh
mkdir -p build reports
g++ -std=c++17 -O2 -shared -fPIC -ffp-contract=off -fno-fast-math \
    -Wall -Wextra -Werror tests/stop_math_probe.cpp -o build/stop_math_probe.so
python tests/validate_stop_math.py --donor /path/to/csgo/nl.bin
```

Оракул проверяет хеш донора и исполняет только ограниченные участки x86-кода.
Контекст игры заменён фикстурами; DllMain и загрузчик не выполняются.
