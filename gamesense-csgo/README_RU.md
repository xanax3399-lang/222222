# Skeet v2: восстановление точек NL для CS:GO

Основа — пользовательский `Skeet_NL_Hypotheses_8802.rar`. Исходные файлы
оболочки импортированы отдельно; их хеши находятся в `archive_baseline.json`.
Исторические утверждения и инструкции архива сохранены в `ARCHIVE_README_RU.md`.
Они не являются результатами новой проверки.

**Нового игрового DLL-патча пока нет.** `nl_points.h` — компилируемый C++-модуль
геометрии и масштаба точек, который ещё не вызывается из GS. Прицеливание,
выбор цели/записи/точки, hitchance и существующие режимы оболочки не изменены.
Код и данные CS2 не использованы.

Восстановлено по x86-ядру NL для CS:GO с SHA-256
`682ce73b371349f87da6fd9365f8550e240dcdb97951e80445e70286275ad96e`:

| Часть | Результат и граница проверки |
|---|---|
| Геометрия головы, `0x414AC630` | Центр + четыре основные точки; в полном режиме ещё две диагональные. Сравнение с нативными инструкциями генератора и его пересечения капсулы. Масштаб задан одинаковым явным входом. |
| Геометрия тела, `0x41490FA0` | Центр + две боковые; для hitbox 6 дополнительная верхняя точка. В тесте отсутствующая функция `client.dll` заменена внутренним пересечением капсулы NL. Эквивалентность именно игровой функции не установлена. |
| Масштаб, `0x4149ED20` | Ручной процент, автоматическое сжатие по расстоянию и разбросу, ограничение масштаба. В эмуляторе выполняется родная CRT-функция синуса. Возвращаемый результат отдельного оружейного helper в fallback-ветке задаётся входом теста. |
| Пересечение капсулы в новом C++ | Собственная аналитическая реализация; не буквальная декомпиляция SSE-кода. Проверяется сравнением выходных координат. |
| Полное управление генератором | Маска хитбоксов, чтение конфигурации и состояния оружия, выделение памяти и метаданные нативных точек не перенесены. Входы модуля явные. |

Проверены 1000 наборов геометрии, 1000 наборов масштаба и 37 некорректных
входов геометрии. Подробности и ограничения — `reports/points_validation.json`.
Недопустимые/вырожденные входы возвращают `false`, оставляя выходной объект
неизменным. Такой результат должен оставлять управление штатному генератору.

## Почему подключение не включено

Найденный генератор GS `0x433FD9B7` работает с тремя вариантами матриц
анимации; его два прямых вызова — `0x433341CA` и `0x4335E9D0`.
Его временный буфер инициализируется функцией `0x433D5A95`:
`begin = this + 0x10`, `end = begin`, `capacity = begin + 0x48`.
При размере точки `0x18` это **три точки**. NL использует записи размером
`0x50` и может выдавать семь точек. Записать туда результат NL напрямую
означает выйти за границы буфера и потерять смысл метаданных.

Следующий этап интеграции требует восстановить обычный путь кандидатов и
управление его памятью в обоих вызывающих участках, адаптировать метаданные,
сохранить проверки всех вариантов матриц и проверить переходник. Замена
найденного генератора целиком пока не обоснована. Алгоритм выбора точки
прицеливания NL ещё не восстановлен. Эти факты не исправляются успешной
компиляцией DLL.

## Воспроизведение проверки математики

На Linux с Python 3 и g++:

```sh
python -m venv .venv
.venv/bin/pip install unicorn==2.1.4
mkdir -p build reports
g++ -std=c++17 -O2 -shared -fPIC -ffp-contract=off -fno-fast-math \
    -Wall -Wextra -Werror tests/points_probe.cpp -o build/points_probe.so
.venv/bin/python tests/validate_points.py --donor /path/to/nl.bin
g++ -std=c++17 -O2 -ffp-contract=off tests/points_smoke.cpp -o build/points_smoke
./build/points_smoke
python tests/validate_points_contract.py
```

Донор сверяется по SHA-256 до выполнения любых инструкций. Семь изменений
нормализации из исходной оболочки перечислены с исходными байтами в
`recovery/nl_geometry_patches.json`. Изменения применяются только к копии
образа в эмуляторе. DLL инициализация, инъекция и игра не запускаются.

GitHub Actions собирает модуль и запускает эти проверки. Его артефакт
содержит исходный код и отчёты, без нового игрового DLL или инжектора.
