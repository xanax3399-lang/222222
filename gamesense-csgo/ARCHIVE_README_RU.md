# Skeet 8802 — NL animation hypotheses, диагностика краша r3

Встроена одна восстановленная ветка генерации углов анимации Neverlose в нативный путь построения дополнительных матриц Skeet. Это **частичный перенос**, а не полный resolver или Ragebot Neverlose. Точность в игре ещё не измерена.


## Вход на карту: диагностика r3

Подтверждено пользователем: режим 1 заходит на карту, режим 2 вызывает access violation по адресу `0x433d5f12`. В этой инструкции читается байт по адресу `ECX + 0x4347be0a`. На скрине нет регистров и адреса неудачного обращения, поэтому причина сбоя пока не установлена.

В r3 добавлен журнал `skeet_crash.log` рядом со `skeet.dll`: параметры исключения, регистры, ограниченный фрагмент стека, инструкции в месте сбоя, счётчики и последняя стадия вызова экспериментальной ветки. Снимок последнего вызова приблизительный, при работе нескольких потоков это не полная трасса. Алгоритм и точка подключения r2 не изменены. Исключение не подавляется и регистры при ошибке не исправляются.

Проверка для сбора данных:

1. Полностью закрой игру и распакуй архив в новую папку.
2. Используй оба новых файла из `bin`, запусти `injector.exe`, выбери 2.
3. Для воспроизведения достаточно локальной карты с ботами.
4. Если появится окно ошибки, дождись строки `Report saved: skeet_crash.log`.
5. Пришли **`bin/skeet_crash.log` и `bin/loader_last.log`**. Журнал сбоя сохраняется до нажатия OK в окне ошибки.
6. Если файл не появился, скопируй полный текст окна через Ctrl+C: в r3 там также есть ECX и ESP.

До установления причины для обычной игры используй режим 1 после полного перезапуска. Успешные тесты ниже проверяют сборку и диагностический код, а не стабильность режима 2 на карте.

## Исправление запуска r2

В прежней сборке экспериментальная ветка устанавливалась после расчёта контрольной суммы ядра. Переход менял байты в проверяемом диапазоне, и сохранённая сумма переставала соответствовать коду. Это могло приводить к отсутствию меню после открытия игры.

Теперь сначала устанавливается выбранный модуль, затем выполняются штатные расчёт суммы и подготовка VM. Порядок проверен на скомпилированном установщике с оригинальной x86-функцией суммы `0x4333d6a2`. Проверены штатный и экспериментальный режимы, отклонение неподдерживаемых входов, ошибки выделения/защиты памяти и сброса кеша, восстановление исходных инструкций при отказе.

Лоудер сохраняет `loader_last.log` рядом с `injector.exe`: выбранный режим, этап загрузки и сообщение DLL с кодом. Отказы установки теперь имеют отдельные сообщения. Пункт 3 читает диагностику и не перезаписывает журнал запуска. Подтверждения успешного запуска в самой игре здесь пока нет.

## Запуск

1. Распакуй архив в отдельную папку. Используй **оба новых файла из `bin` этой сборки**: `injector.exe` и `skeet.dll`.
2. Перед первым запуском и перед сменой режима полностью закрой CS:GO. Лоудер выбирает режим до инициализации ядра.
3. Открой терминал в `bin`, выполни `injector.exe` и выбери:
   - **1 — GameSense**: исходный игровой алгоритм, новый модуль не устанавливается.
   - **2 — NL animation hypotheses**: экспериментальный модуль генерации гипотез.
   - **3 — Read active module diagnostics**: прочитать счётчики уже загруженной сборки.
4. Для проверки режима 2 зайди на карту с противниками, затем снова запусти лоудер и выбери 3. В главном меню вызовов может не быть.

Можно запускать без меню:

```text
injector.exe --mode stock
injector.exe --mode nl-hypotheses
injector.exe --diagnostics
```

Если игра открылась, но меню снова не появилось, пришли `bin/loader_last.log`. Нужен полный журнал, а не только последняя строка.

Параметр `--game "полный путь к csgo.exe"` можно добавить к запуску выбранного режима. Цель — только соответствующая x86 CS:GO Legacy 8802.

## Что проверять в диагностике

- `Mode`: выбранный режим.
- `Installed: 1`: переход установлен; это ещё не подтверждение вызова на карте.
- `Builder calls`: сколько раз выполнена точка подключения.
- `Hypotheses supplied`: сколько входов прошло проверки и получило рассчитанный угол.
- `Rejected inputs`: сколько вызовов оставлено штатной логике из-за неподдерживаемого контекста/входа.
- `Last sample`: номер варианта GS, тик записи, базовый и переданный углы.

Положительные счётчики подтверждают выполнение кода. Они не доказывают улучшение попаданий. Перед дальнейшим подключением истории и выбора гипотез нужны результаты этой проверки в игре: вывод пункта 3 и наличие ошибок/вылетов после появления противников.

## Граница переноса

| Часть | Состояние |
|---|---|
| Ветка Neverlose без сохранённых углов из `0x41339870`, `EDX == 0` | Восстановлена и подключена |
| Порядок вариантов GS | Адаптер: GS 0 → NL 1 (+60), GS 1 → NL 3 (−30), GS 2 → NL 2 (−60) |
| Предел угла | Ограничен положительным/отрицательным пределом, который вычислил сам Skeet |
| Перестроение поз и матриц | Выполняет штатный Skeet после передачи угла |
| Выбор окончательной гипотезы, учёт промахов, выбор записи/точки, hitchance | Остаются штатными GS |
| Коллектор кандидатов Neverlose и ветка с сохранёнными углами | В этой сборке не подключены |
| Полный resolver/Ragebot Neverlose | Не перенесён |

Соответствие трёх вариантов и ограничение диапазона — решения адаптера. Это не заявление о переносе всего алгоритма 1:1. Никаких выводов об отсутствии resolver в Neverlose из найденной ветки сделать нельзя.

## Подключение

В режиме 2 заменяются 13 байт в общей точке `0x433fb4be`, после нормализации угла и перед публикацией в запись. Обе исходные инструкции исполняются в переходнике, возврат — `0x433fb4cb`. Условный путь, который обходит запись по `0x433fb4b8`, тоже попадает в новую общую точку.

Регистр XMM1 и копия угла на стеке получают согласованное значение. Общие регистры, флаги, остальные части SSE/x87 и управляющие слова сохраняются. Перед вызовом C++ используется отдельное сохранённое состояние и пустой рабочий стек FPU. Установка выполняется до запуска исходного entry, а не во время игры. Выбор режима передаётся в проверяемом маркере резервирования; нужны согласованные injector/DLL этой версии.

Вложенный `Binary/skeet.bin` остаётся побайтно исходным. Проверяется его отпечаток и точные инструкции в точке подключения. Предыдущие AI-модули из очищенной базы не возвращены.

## Проверки и воспроизведение

В `reports` лежат результаты фактических проверок этой сборки. Эмуляция исполняет скомпилированный Windows C++ переходник, исходные инструкции публикации угла и проверяет варианты, семь вызывающих адресов, оба направления флага DF, полный стек x87, нестандартное округление и оба пути к общей точке.

Обнаруженная отдельно особенность Unicorn 2.1.4: FXRSTOR не восстанавливает x87 FIP. Четыре соответствующих байта исключены из сравнения переходника после независимого воспроизведения; значения x87, теги, управляющее слово, MXCSR и XMM сравниваются. Отдельный тест на реальном хосте сравнивает все 512 байт FXSAVE/FXRSTOR. Это не запуск игры на Windows.

Сборка и проверки в Linux x86_64, Python 3, g++ для независимого теста FPU:

```sh
python3 -m pip install -r requirements-build.txt
python3 build_windows.py
python3 tests/verify_clean_release.py
python3 tests/validate_resolver.py
python3 tests/validate_core_image.py
python3 tests/validate_launcher.py
python3 tests/validate_hypotheses.py
python3 tests/validate_hypotheses_startup.py
python3 tests/validate_crash_report.py
```

Название `validate_resolver.py` унаследовано от базы: этот тест проверяет разрешение адресов Steam overlay, а не игровой resolver. Для побитного сравнения с оригинальной веткой дополнительно: `python3 tests/validate_hypotheses.py --donor /path/to/nl.bin`. Нужен донор с SHA-256 `682ce73b371349f87da6fd9365f8550e240dcdb97951e80445e70286275ad96e`; бинарник Neverlose в архив не включён.

Windows loader и игра здесь не запускались. Успешные проверки не являются подтверждением роста точности или отсутствия вылетов на сервере.
